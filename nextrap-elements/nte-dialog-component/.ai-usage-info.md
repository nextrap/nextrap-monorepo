# AI usage information: @nextrap/nte-dialog-component

Use this package for typed, programmatic dialogs in applications and SPAs.

For Markdown, CMS content, static/declarative HTML, launcher slots, URL hash/anchor opening, or direct use of a dialog element, use `@nextrap/nte-dialog` instead.

## Architecture

`NteDialogComponent<TInput, TResult>` is an application abstraction built on `@nextrap/nte-dialog`. It owns:

- temporary mounting into `document.body` via static `show()`
- typed input
- Promise-based typed results
- `submit()` / `abort()` completion
- rendering title/body/footer as light-DOM content of an inner `NteDialog`
- cleanup after completion

It does not own launcher, anchor/hash routing, native dialog rendering, backdrop handling or visual Sass implementation. Those belong to `@nextrap/nte-dialog`.

## Generic type contract

The two generics are deliberately strict and must remain connected through the complete dialog lifecycle:

```ts
NteDialogComponent<TInput, TResult>
```

`TInput` is the exact value required by `show()` and `open()`. Only `TInput = void` removes the argument entirely:

```ts
class UserEditDialog extends NteDialogComponent<{ userId: string }, User> { ... }

UserEditDialog.show({ userId: '123' }); // correct
UserEditDialog.show();                  // must be a TypeScript error
```

Do **not** change the non-void input tuple from `[input: TInput]` to `[input?: TInput]`. An optional argument would make the main input guarantee ineffective: a dialog declaring `{ userId: string }` could then be opened without a user ID and would fail only at runtime.

`TResult` must likewise remain the type used by `submit()`, the internal resolver/promise and the public result Promise. Do **not** replace the internal resolver or Promise with `any` and cast it back at the API boundary. That would break the end-to-end relationship the abstraction is intended to guarantee:

```text
TInput  -> show/open -> this.input
TResult -> submit    -> resolver -> Promise result.data
```

Tests must conform to this contract rather than weakening production generics to make a test compile. For a dialog with no input or no submitted payload, use `void` explicitly or rely on the default generic:

```ts
class ConfirmDialog extends NteDialogComponent<void, void> { ... }
const result = await ConfirmDialog.show();
```

## Basic pattern

```ts
class UserEditDialog extends NteDialogComponent<{ userId: string }, User> {
  protected override renderTitle() {
    return html`Edit user`;
  }

  protected override renderDialog() {
    return html`<user-editor .userId=${this.input.userId}></user-editor>`;
  }

  protected override renderFooter() {
    return html`
      <button @click=${this.abort}>Cancel</button>
      <button @click=${() => this.submit(user)}>Save</button>
    `;
  }
}

const result = await UserEditDialog.show({ userId: '123' });
if (result.submitted) {
  use(result.data);
}
```

## Result contract

```ts
type NteDialogComponentResult<T> =
  | { submitted: true; data: T }
  | { submitted: false };
```

Keep `submitted` as the discriminator. Do not add parallel `aborted`, `saved`, or status-enum fields without intentionally redesigning the public API.

## Void input and result

Both generics default to `void`:

```ts
class ConfirmDialog extends NteDialogComponent { ... }
const result = await ConfirmDialog.show();
```

For `TResult = void`, use `this.submit()` with no dummy payload.

## Rendering contract

Derived classes override:

- `renderDialog()` — required body content
- `renderTitle()` — optional title
- `renderFooter()` — optional footer/actions

The base class owns `render()` and renders into its own light DOM by overriding `createRenderRoot()` to return the host. Do not move the generated dialog content into an additional component Shadow DOM by default.

The resulting structure is conceptually:

```html
<user-edit-dialog>
  <nte-dialog>
    <div slot="title">...</div>
    <!-- renderDialog() output -->
    <div slot="footer">...</div>
  </nte-dialog>
</user-edit-dialog>
```

Therefore the values returned by `renderTitle()`, `renderDialog()` and `renderFooter()` become light-DOM descendants and are projected through the normal slots of `NteDialog`. `NteDialog` itself continues to own its internal Shadow DOM and native `<dialog>` rendering.

This is intentional: application content remains directly accessible to application CSS, DOM integrations and components that expect light-DOM ancestry, while the reusable dialog chrome stays encapsulated.

## Options

```ts
protected override dialogOptions = {
  dialogClass: ['size-lg', 'with-shadow'],
  dismiss: {
    closeButton: true,
    escape: true,
    backdrop: 'shake',
  },
};
```

`dialogClass` is the bridge to the visual API from `@nextrap/nte-dialog`. Keep visual concerns such as size, shadow and highlighted appearance in CSS/Sass rather than adding TypeScript behavior options.

`dismiss` controls application-level dismiss behavior. An accepted dismiss resolves the dialog through `abort()`.

## Cross-package guidance

Use `@nextrap/nte-dialog-component` when the requirement contains concepts such as:

- open a dialog from TypeScript/application code
- typed input
- await a result
- Promise
- submit/cancel result
- SPA workflow

Use `@nextrap/nte-dialog` when the requirement contains concepts such as:

- Markdown or CMS page
- declarative HTML
- launcher/opener element
- `#modal:...` anchor
- direct `<nte-dialog>` markup

Do not add launcher or anchor APIs to this package. If such behavior is needed, compose/use `NteDialog` directly.

When changing the public programmatic API or rendering model, update this file and the README examples together.
