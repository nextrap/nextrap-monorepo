# @nextrap/style-base

## Purpose

Provides the global Nextrap design-token contract. There is exactly one theme engine: `runtime-theme()`. It emits defaults and derives related values from CSS custom properties so themes can be changed at runtime without Sass theme maps or recompilation.

Use this package once at document/theme level. Components consume `var(--nt-*)`; they must not depend on private Sass theme state.

## Theme creation contract

### Standard/default theme

Use the ready-to-use default entry point:

```scss
@use '@nextrap/style-base/default';
```

`default.scss` emits `runtime-theme()` on `:root` and the explicit scheme selectors. Use it when no separate application/external theme owns the token overrides.

### Custom theme

```scss
@use '@nextrap/style-base' as nt;

:root {
  @include nt.runtime-theme();

  // Theme-owned inputs come after the mixin.
  --nt-primary: #0057b8;
  --nt-neutral: #667085;
  --nt-radius: .5rem;
  --nt-font-family: Inter, sans-serif;
}

@include nt.runtime-scheme-selectors();
```

Always emit `runtime-theme()` first and declare theme overrides afterwards in the same scope. Do not copy the generated token graph into a theme repository. Override the smallest set of input variables the theme actually owns; derived tokens then update automatically.

A derived variable may be overridden only when the design intentionally differs from the standard derivation.

### External theme repository

An external theme package should depend on `@nextrap/style-base`, call `runtime-theme()` in its theme scope, and contain only its owned CSS-variable overrides. This keeps the external theme automatically compatible when style-base adds or fixes derived tokens.

### Scoped themes

`runtime-theme()` can be emitted on `:root`, a theme class or another ancestor scope. All descendant Nextrap components inherit the resulting `--nt-*` contract.

### Color schemes

The runtime graph uses `color-scheme: light dark`, `light-dark()` and runtime color derivation. OS preference therefore needs no separate theme generation.

Emit `runtime-scheme-selectors()` once when the application must explicitly force a scheme, then use `data-nt-scheme="light"` or `data-nt-scheme="dark"` on an ancestor.

Theme inputs can themselves be scheme-aware:

```css
--nt-primary: light-dark(#0057b8, #65b7ff);
```

## Token usage contract

### Brand and state inputs

| Variable | Intended usage |
|---|---|
| `--nt-primary` | Main brand/action color: primary buttons, selected states, key actions. |
| `--nt-secondary` | Secondary actions and UI where primary emphasis would be too strong. |
| `--nt-tertiary` | Optional third brand/semantic family for differentiated groups or actions. |
| `--nt-accent` | Highlights and complementary brand emphasis. |
| `--nt-success` | Positive states, confirmations and completed outcomes. |
| `--nt-info` | Informational notices, callouts and neutral status UI. |
| `--nt-warning` | Cautionary states that need attention but are not errors. |
| `--nt-danger` | Destructive actions, validation errors and critical states. |
| `--nt-neutral` | Neutral seed used to derive surfaces, text, borders and the gray ramp. |
| `--nt-light` / `--nt-dark` | Explicit light/dark utility colors where a semantic surface is not appropriate. |
| `--nt-white` / `--nt-black` | Absolute contrast endpoints and explicit white/black usage. |

Each semantic color family provides `-hover`, `-active`, `-subtle` and `-emphasis` variants. Use `-hover`/`-active` for interaction feedback, `-subtle` for tinted backgrounds and `-emphasis` for stronger borders/text/details.

`--nt-text-on-primary`, `--nt-text-on-secondary`, `--nt-text-on-tertiary`, `--nt-text-on-accent`, `--nt-text-on-success`, `--nt-text-on-info`, `--nt-text-on-warning`, `--nt-text-on-danger`, `--nt-text-on-light`, `--nt-text-on-dark`, `--nt-text-on-white` and `--nt-text-on-black` are foreground colors for content rendered directly on the corresponding background.

### Surfaces and content

| Variable | Intended usage |
|---|---|
| `--nt-surface` | Default page or component background. |
| `--nt-surface-muted` | Recessed/secondary areas, grouped content and subtle panels. |
| `--nt-surface-raised` | Cards, popovers, dialogs and visually elevated surfaces. |
| `--nt-text` | Default readable foreground text. |
| `--nt-text-muted` | Descriptions, metadata, helper text and secondary copy. |
| `--nt-header` | Heading foreground where headings need a theme-specific color. |
| `--nt-border` | Standard component borders and dividers. |
| `--nt-focus` | Keyboard/focus-visible rings and accessibility focus indicators. |
| `--nt-link` | Default link foreground. |
| `--nt-link-hover` | Link hover feedback. |
| `--nt-link-active` | Pressed/active link feedback. |

### Typography

| Variable | Intended usage |
|---|---|
| `--nt-font-family` | Default body and control font family. |
| `--nt-font-family-header` | Heading/display family; defaults to the base family. |
| `--nt-font-size` | Base text size and reference for the text scale. |
| `--nt-font-size-header` | Maximum heading size (`h1`); heading scale interpolates down from it. |
| `--nt-font-size-small` | Captions, metadata, helper and supporting text. |
| `--nt-font-weight-base` | Normal body/control weight. |
| `--nt-font-weight-header` | Default heading weight. |
| `--nt-font-weight-bold` | Strong emphasis/bold weight. |
| `--nt-line-height` | Body/control line height and text-rhythm baseline. |
| `--nt-line-height-header` | Compact heading/display line height. |

`--nt-fs-1 … --nt-fs-6` form the derived general text scale. `--nt-fs-h1 … --nt-fs-h6` form the heading scale. Prefer them when a component needs a shared scale step instead of inventing a local size.

### Shape

| Variable | Intended usage |
|---|---|
| `--nt-radius` | Theme-level base radius. Override this to change overall UI roundness. |
| `--nt-border-radius-sm` | Tags, badges, compact controls and other small elements. |
| `--nt-border-radius` | Default component radius derived from `--nt-radius`. |
| `--nt-border-radius-xl` | Large cards, dialogs, panels and prominent surfaces. |
| `--nt-border-width` | Standard component/divider border thickness. |

## Spacing system

### Primitive spacing

`--nt-space-0 … --nt-space-10` are the shared primitive scale. Use a primitive when an exact scale step is intentionally part of a component design contract. Application/layout code should normally prefer semantic tokens.

| Variable | Default | Typical usage |
|---|---:|---|
| `--nt-space-0` | `0` | Reset/no spacing. |
| `--nt-space-1` | `.25rem` | Micro gaps and tiny icon adjustments. |
| `--nt-space-2` | `.5rem` | Tight icon/text gaps and compact internals. |
| `--nt-space-3` | `.75rem` | Small control spacing/padding reference. |
| `--nt-space-4` | `1rem` | Normal text rhythm and common base gaps. |
| `--nt-space-5` | `1.5rem` | Component padding and container gutter reference. |
| `--nt-space-6` | `2rem` | Gaps between sibling components/content regions. |
| `--nt-space-7` | `3rem` | Compact major-section separation. |
| `--nt-space-8` | `4rem` | Major layout/section separation. |
| `--nt-space-9` | `6rem` | Large page-section separation. |
| `--nt-space-10` | `8rem` | Hero and maximum standard page-region spacing. |

### Semantic spacing — preferred

| Variable | Scope | Use for | Do not primarily use for |
|---|---|---|---|
| `--nt-spacing-text` | Typography/content | Vertical rhythm between paragraphs, lists, prose blocks, stacked labels and related textual elements. | Card padding or page sections. |
| `--nt-spacing-control` | Controls | Button/input internal spacing reference, icon-to-label gaps, compact toolbars and gaps between tightly related controls. | General card padding or page layout. |
| `--nt-spacing-component` | Component internals | Card/dialog/panel padding and spacing between regions belonging to the same component. | Distance between independent cards/sections. |
| `--nt-spacing-layout` | Layout composition | Grid/flex gaps between sibling components, cards, columns and independent content regions. | Internal button/input spacing. |
| `--nt-spacing-section` | Page composition | Vertical separation between major page sections, landing-page bands and large content chapters. | Component internals. |

Mental model: **text → control → component → layout → section**. Moving right increases visual distance and structural scope.

```css
.article-copy > * + * { margin-block-start: var(--nt-spacing-text); }
.toolbar { gap: var(--nt-spacing-control); }
.card { padding: var(--nt-spacing-component); }
.card-grid { gap: var(--nt-spacing-layout); }
.page-section + .page-section { margin-block-start: var(--nt-spacing-section); }
```

## Container

| Variable | Intended usage |
|---|---|
| `--nt-container-max` | Maximum width of centered page/content containers. |
| `--nt-container-gutter` | Horizontal inset between container content and viewport edge. |
| `--nt-container-width` | Computed responsive width for consumers that want a single ready-to-use width token. |

```css
.container {
  width: min(calc(100% - 2 * var(--nt-container-gutter)), var(--nt-container-max));
  margin-inline: auto;
}
```

## Neutral gray scale

`--nt-gray-100 … --nt-gray-900` are derived from `--nt-neutral`. Use them for neutral component details when `surface`, `text`, `text-muted` or `border` do not express the required intent. Prefer semantic tokens whenever one fits.

## Architecture contract

- There is one theme engine: `runtime-theme()`.
- Do not introduce Sass theme maps, compile-time theme builders or a parallel token generator.
- `@nextrap/style-base/default` must remain the ready-to-use standard theme.
- Include style-base once at document/theme level; never include it inside component shadow-DOM styles.
- Components consume `var(--nt-*)`; cross-package interoperability is CSS-token based.
- Theme repositories override input custom properties after `runtime-theme()` and normally leave derived variables untouched.
- Do not emit resets, native-element styling, utility classes or component styling from style-base.
