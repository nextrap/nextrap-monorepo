# @nextrap/style-utils

## Purpose

Provides reusable Nextrap utility classes for styling individual elements directly in markup. Utilities consume the runtime CSS tokens from `@nextrap/style-base` and must not introduce a second theme system.

## Important rules

**Use these styles in HTML and Markdown to style individual elements.** Prefer an existing utility over a one-off helper class.

For colors, keep these concepts separate:

1. **`.bg-*` = background only.** It must not implicitly change text color.
2. **`.surface-*` = complete readable surface.** It sets a semantic background and its matching `--nt-text-on-*` foreground.
3. **`.scheme-light` / `.scheme-dark` = local light/dark evaluation context.** They change `color-scheme` for an element and its descendants but do not choose a background.

Do not add a magical `text-auto` utility that tries to inspect the computed DOM background. CSS cannot reliably use an arbitrary computed `background-color` as an input. Use an explicit `surface-*` pair instead.

## Import

Ready-to-use classes:

```scss
@use '@nextrap/style-utils/default';
```

Mixin API:

```scss
@use '@nextrap/style-utils' as u;
```

Scoped complete utility output:

```scss
.theme {
  @include u.utils();
}
```

## Color utilities

### Atomic backgrounds

`.bg-*` changes only `background`. Use it when foreground is intentionally controlled elsewhere.

Examples:

- `.bg-primary`, `.bg-secondary`, `.bg-tertiary`, `.bg-accent`
- `.bg-success`, `.bg-info`, `.bg-warning`, `.bg-danger`
- `.bg-light`, `.bg-dark`, `.bg-white`, `.bg-black`
- semantic `-subtle` and `-emphasis` variants
- deprecated `.bg-soft-*` aliases map to subtle tokens

Do **not** automatically add `color` to `bg-*`; that would make an atomic background helper surprising and break compositions that intentionally choose their own foreground.

### Semantic readable surfaces

Use `.surface-*` when the background itself defines the readable foreground. Typical uses: colored/inverted page sections, heroes, callouts, cards, badges or controls.

Available classes/mixins:

- `.surface-primary` / `surface-primary()` → `--nt-primary` + `--nt-text-on-primary`
- `.surface-secondary` / `surface-secondary()` → `--nt-secondary` + `--nt-text-on-secondary`
- `.surface-tertiary` / `surface-tertiary()` → `--nt-tertiary` + `--nt-text-on-tertiary`
- `.surface-accent` / `surface-accent()` → `--nt-accent` + `--nt-text-on-accent`
- `.surface-success` / `surface-success()` → `--nt-success` + `--nt-text-on-success`
- `.surface-info` / `surface-info()` → `--nt-info` + `--nt-text-on-info`
- `.surface-warning` / `surface-warning()` → `--nt-warning` + `--nt-text-on-warning`
- `.surface-danger` / `surface-danger()` → `--nt-danger` + `--nt-text-on-danger`
- `.surface-light` / `surface-light()` → `--nt-light` + `--nt-text-on-light`
- `.surface-dark` / `surface-dark()` → `--nt-dark` + `--nt-text-on-dark`
- `.surface-white` / `surface-white()` → `--nt-white` + `--nt-text-on-white`
- `.surface-black` / `surface-black()` → `--nt-black` + `--nt-text-on-black`

Example:

```html
<section class="surface-primary">
  <h2>Readable primary section</h2>
  <p>Foreground follows --nt-text-on-primary automatically.</p>
</section>
```

Sass:

```scss
.hero {
  @include u.surface-primary();
}
```

The `--nt-text-on-*` values belong to style-base. Components/utilities consume them; they must not independently decide black/white contrast.

## Local light/dark scheme

A scheme may be switched for a **section/subtree**, not only for the page. `color-scheme` is inherited, so scheme-aware tokens using `light-dark()` and descendant components evaluate against the nearest forced scheme.

```html
<section class="scheme-dark surface-dark">
  This subtree is forced to dark mode and has a dark readable surface.
</section>
```

The concepts are independent:

- `.surface-dark` sets a concrete dark background + matching foreground, but does not mean every descendant should evaluate its scheme-aware tokens as dark.
- `.scheme-dark` sets `color-scheme: dark`, but does not choose a background.
- Combine them for a fully inverted section.

A nested subtree can switch back:

```html
<section class="scheme-dark surface-dark">
  Dark subtree
  <aside class="scheme-light surface-light">Locally light subtree</aside>
</section>
```

Available classes/mixins:

- `.scheme-light` / `scheme-light()`
- `.scheme-dark` / `scheme-dark()`

## Web Types / IDE contract

Public utility classes must be represented in the package Web Types metadata so JetBrains IDE completion and documentation match the Sass/CSS API.

- `web-types.json` is the established utility catalog.
- `web-types.surfaces.json` describes the semantic `surface-*` and `scheme-*` API.
- `package.json#web-types` intentionally lists both files. JetBrains supports an array of Web Types paths; do not collapse it to a single path unless the manifests are merged.
- `vite.config.ts` must copy `web-types*.json` into the build output. The published `package.json` resolves these paths relative to the package root, so a manifest present only in source but missing from `dist` is a packaging bug.

Whenever a public utility is added, removed or renamed, update its Web Types metadata in the same change. Keep descriptions semantic: explain whether a utility changes only one CSS property (`bg-*`), establishes a readable background/foreground pair (`surface-*`), or changes the inherited scheme context (`scheme-*`).

## Text colors

Use `.text-primary`, `.text-secondary`, `.text-tertiary`, `.text-accent`, `.text-success`, `.text-info`, `.text-warning`, `.text-danger`, `.text-light`, `.text-dark`, `.text-white`, `.text-black` when a specific foreground is explicitly intended.

For ordinary body/heading text, prefer the semantic style-base values inherited from the active surface/scheme rather than hard-coded text utilities.

## Gray utilities

- Backgrounds: `.bg-gray-100` ... `.bg-gray-900`
- Text: `.text-gray-100` ... `.text-gray-900`

## Spacing

- Margin: `.m-0` ... `.m-5`, directional/x/y variants and `auto` variants where provided
- Padding: `.p-0` ... `.p-5`, directional/x/y variants
- Gap: `.gap-0` ... `.gap-5`, `.gap-x-*`, `.gap-y-*`

Spacing utilities must continue to resolve to style-base spacing tokens rather than package-local design scales.

## Other utility groups

The package also provides the existing display, flex, grid/row, border/radius, font, text, list, dimension, container and table utilities. Keep their public class/mixin parity intact.

## Architecture contract

- Follow `docs/style-packages-architecture.md`.
- Public utility classes should have same-named public mixins where meaningful.
- Class output must be generated from those mixins (single source of truth).
- Base/modifier composition and arbitrary-selector Sass usage must remain possible.
- Keep token usage based on `var(--nt-*)` interoperability.
- `bg-*`, `surface-*`, and `scheme-*` are deliberately different APIs; do not collapse their responsibilities.
- Web Types metadata is part of the public package contract and must survive the build/publish pipeline.
